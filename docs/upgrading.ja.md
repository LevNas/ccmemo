# アップグレード

> English version: [upgrading.md](upgrading.md)

ccmemo を更新した、あるいはこれから更新する人のためのページです。  
この記事では更新のあとにナレッジベース側で作業が要るかどうかと、作業する場合の手順をまとめています。  
ほとんどの更新では何もする必要がありません。

## このページで使う言葉

| 用語 | 意味 |
|---|---|
| ナレッジベース | プロジェクトの `.claude/knowledge/` フォルダ。 |
| エントリ | ナレッジベースの中の Markdown ファイル 1 つ。 |
| frontmatter | エントリ先頭の `---` で挟まれた部分。 |
| lint | `kb_graph.py lint` で実行する検査。pre-commit から実行している人もいます。 |

## 何かする必要はあるか

| 更新前のバージョン | 読む場所 |
|---|---|
| 1.27.0 以降 | 何もありません。 |
| 1.26.x | [1.27: エントリの id と検証の記録](#127-エントリの-id-と検証の記録)。コマンド 1 回と 1 行の書き込みです。しなくても壊れません。 |
| 1.25.x または 1.24.x | 上の節に加えて [1.26: description とリンクの理由](#126-description-とリンクの理由)。作業は任意で、しなくても壊れません。 |
| 1.23.x 以前 | 上の 2 節に加えて [1.24: tags と status](#124-tags-と-status)。作業は不要ですが、挙動が 2 つ変わります。 |

## 自動で済むこと

**プラグイン本体。**  
`/plugin update ccmemo` で新しい版が取得され、`/reload-plugins` で実行中のセッションに反映されます。  
更新そのものはこれで終わりです。

**検索用の索引。**  
ccmemo は `.claude/knowledge/.index/` に検索用の索引を持っています。  
新しい版で索引の形式が変わった場合も、次の検索のときに Markdown から必要な分だけ作り直されます。  
手で作り直すことはありません。

**エントリの規則は自分で有効にする。**  
lint はエントリを一連の規則に照らして検査し、新しい版では規則が増えることがあります。  
増えた規則は、ナレッジベースがその規則に従うと宣言するまで lint を失敗させません。  
宣言は、`.claude/knowledge/CLAUDE.md` の先頭に規則の版を書くことで行います。

```yaml
---
schema_version: 2
---
```

宣言するまでの間、lint は新しい規則で引っかかる箇所も一覧に出しますが、「advisory」（参考）という見出しの下に出し、終了コードは 0 のままです。  
そのため、更新しただけで pre-commit の検査が失敗することはありません。  
宣言する前に新しい規則の結果を見たいときは、`kb_graph.py --schema 2 lint` を実行します。

## 1.27: エントリの id と検証の記録

### 何が変わったか

すべてのエントリが **id** を持つようになりました。  
frontmatter の `id:` に一度だけ書かれる、ランダムな識別子です。  
ファイル名は「いつ作ったか」と「何についてか」を表し、id は「どのエントリか」を表します。  
そのため、ファイルを改名したり別のナレッジベースへ複製したりしても、同じエントリだと追えます。  
`kb_graph.py rename` はスラッグを変えて、そのエントリへのリンクをすべて書き換えます。  
`kb_graph.py relink` は、手作業で移動したファイルへのリンクを直します。

また、**誰が書いたか**と**誰が確かめたか**を分けて記録するようになりました。  
`generated:` には書き手（人、Claude、または処理）と日時が入ります。  
`verified:` は独立した確認の一覧で、`kb_graph.py verify` で追記します。手で書くことはありません。  
検索結果では、確認済みのエントリのタイトルの後ろに `[human]` または `[machine]` が付き、`--verified human` で絞り込めます。  
従来の `confidence:` は廃止です。書き手の自己評価は確認として数えていなかったためです。  
消す必要はありません。

以上が規則の版 3 です。  
`schema_version: 3` を宣言するまで、新しい 2 つの検査（`missing-id`、`missing-generated`）は参考扱いです。  
`/record-knowledge` で新しく作るエントリは、最初から両方の項目を持っています。

### 更新後に気づくこと

- `kb_graph.py lint` が、id または `generated:` の無いエントリを advisory の見出しの下に一覧します。終了コードは変わりません。  
- Claude が古いエントリを編集すると、「検査はまだ強制されていない」という 1 行の通知が出ます。  
- 検索結果の表示は、エントリが確認されるまで何も変わりません。

### 新しい規則を採用するときの手順

1. すべてのエントリに 2 つの項目を足します。  
   コマンド 1 回で終わり、もう一度実行しても何も変わりません。

   ```bash
   python3 scripts/kb_graph.py --root .claude/knowledge/entries migrate --to 3 --tz +09:00
   ```

   `--tz` はエントリを書いたタイムゾーンです。  
   ファイル名の日時を `generated.at` に変換するためだけに使います。  
   各エントリに `id` と、書き手を `claude-code` とする `generated` が入ります（自分で書いたなら `--by human:<handle>`）。  
   ファイルのほかの部分には触れません。  
   確認済みの印はどのエントリにも付きません。古いエントリはまだ誰も確かめていないからで、それを正直に表すのがこの項目の目的です。

   ```yaml
   # 変更前
   title: プラグインキャッシュはバージョンキー式
   author: "@alice"
   created: 2026-08-11

   # 変更後
   title: プラグインキャッシュはバージョンキー式
   id: 1887fedb-0afd-479e-98ef-e02b80b1fb00
   author: "@alice"
   created: 2026-08-11
   generated:
     by: claude-code
     at: 2026-08-11T17:15:10+09:00
   ```

2. `.claude/knowledge/CLAUDE.md` の先頭の `schema_version: 2` を `3` に書き換えます。  
   以後は id と書き手の項目が必須になり、Claude がエントリを保存した直後にも検査されます。

3. lint を実行して、結果が 0 件であることを確認します。

   ```bash
   python3 scripts/kb_graph.py --root .claude/knowledge/entries lint
   ```

4. 変わったエントリをコミットします。

あとで知っておくことが 2 つあります。  
すべてのエントリの本文が変わったので、次の検索でナレッジベース全体の埋め込みが一度作り直されます。  
数百件で 1 分未満から数分（マシン次第）かかるため、先に `uv run scripts/kb_index.py .claude/knowledge/entries` を自分で実行しておく手もあります。  
もう 1 つは確認の記録です。  
エントリを読んで今も正しいと確かめたら、`python3 scripts/kb_graph.py --root .claude/knowledge/entries verify <entry> --by human:<handle>` で記録します。  
`/review-knowledge` も、レビューで確認したエントリに同じ記録を付けます。  
lint が通ることは確認ではないので、記録しません。

## 1.26: description とリンクの理由

### 何が変わったか

エントリが「どういうときに自分を開くべきか」を持てるようになりました。  
その一文は frontmatter の `description:` に書きます。  
検索結果と、プロンプト送信時に自動で出る候補にこの一文が表示されるので、人も Claude も、複数のエントリを開かずに目当ての 1 本を選べます。  
description が無いエントリもそのまま使えます。  
その場合は本文の最初の段落が `(lead)` という印つきで代わりに表示されます。

エントリ同士のリンク（`- see:`、`- ref:`、`- amends:`、`- extends:`）には、リンクの後ろに短い理由を同じ行に書くことになりました。

```markdown
- see: [プラグインキャッシュはバージョンキー式](2026/08/20260811-171510-alice-plugin-cache.md) — マージした修正が利用側に届かない理由
```

これに伴う新しい規則は 2 つです。  
すべてのエントリに 80〜320 字の description があること、すべてのリンクに理由が付いていることです。  
どちらも規則の版 2 に属するので、`schema_version: 2` を宣言するまでは参考扱いです。  
`/record-knowledge` で新しく作るエントリは、最初からこの 2 つを満たしています。

### 更新後に気づくこと

- `kb_graph.py lint` が、description の無いエントリと理由の無いリンクを advisory の見出しの下に一覧します。終了コードは変わりません。  
- Claude が古いエントリを編集すると、「検査はまだ強制されていない」という 1 行の通知が出ます。

### 新しい規則を採用するときの手順

1. 作業量を把握します。

   ```bash
   python3 scripts/kb_graph.py --root .claude/knowledge/entries --schema 2 lint
   ```

   引っかかるエントリが理由つきで一覧されます。

2. 各エントリに description を書きます。  
   書くのは、そのエントリを開くべき状況です。  
   読み手が見ている症状、抱えている疑問、これから下す判断のどれかを、最もよくある状況から順に並べます。  
   検索結果には先頭 80 字しか表示されないので、順序が効きます。  
   タイトルの繰り返しは書きません。答えはタイトルがすでに述べているからです。

   ```yaml
   # 変更前
   title: プラグインキャッシュはバージョンキー式

   # 変更後
   title: プラグインキャッシュはバージョンキー式
   description: "プラグインの修正を main にマージしたのに利用側で直らないとき、/plugin update が最新と言うのに古い挙動が続くとき、修正 PR にバージョン更新を同梱すべきか迷ったときに開く。"
   ```

   エントリが多い場合は、20〜30 件ずつに分けて Claude に任せると進みます。  
   上の書き方と良い例をいくつか 1 つのファイルにまとめて各回に渡し、終わったら手順 1 のコマンドで確認します。

3. 理由の無いリンクに理由を足します。  
   lint は 1 行ずつ読むので、理由はリンクと同じ行に書きます。

4. 手順 1 の結果が空になったら、`.claude/knowledge/CLAUDE.md` の先頭に `schema_version: 2` を書きます。  
   以後は 2 つの規則が強制され、Claude がエントリを保存した直後にも検査されます。

まとめて編集するときの注意が 1 つあります。  
redact hook を有効にしていると、編集したエントリはすべてその hook を通ります。  
古いエントリに残っていた秘密情報を見つけてくれる利点がある一方で、メールアドレスに似た無害な文字列（`app-foo@autostart.service` のような systemd のユニット名や SSH の URL）を伏せ字にしてしまうことがあります。  
その場合は Edit ツールではなくシェルのコマンドで元に戻します。  
Edit ツールで戻すと hook がもう一度動くからです。

## 1.24: tags と status

ccmemo のすべての部品が同じ方法で frontmatter を読むようになりました。  
書き換えは要りませんが、挙動が 2 つ変わります。

- 1 行に 1 つずつ `"#tag"` を並べたリスト形式の `tags:` を、検索用のスクリプトも読むようになりました。1.24 より前は、リスト形式を「タグ無し」として黙って扱っていました。新しいエントリはリスト形式で書くことを勧めますが、1 行形式の `tags: "#a #b"` も引き続き読めるので、古いエントリはそのままで構いません。  
- `status:` の行が無いエントリは、どの部品でも `active` として扱われます。1.24 より前は、検索用のスクリプトがそうしたエントリを `--status active` から外していました。  
- `#1password` のように数字で始まるタグを認識するようになりました。
